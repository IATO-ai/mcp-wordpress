# IATO WordPress MCP Plugin

WordPress plugin that exposes an MCP server from any self-hosted WordPress.org install, so AI clients (Claude Desktop, Cursor, etc.) can read and write WordPress content. When the user provides an IATO API key, additional bridge tools expose read-only crawl data (SEO issues, sitemap, orphan pages, broken links, suggestions).

MCP server URL once installed: `https://{site}/wp-json/iato-mcp/v1/message`

## Architecture

```
Claude Desktop / AI Client
        |  HTTP MCP transport (Streamable HTTP — one POST per request, no SSE for MVP)
        |
WordPress Plugin (iato-mcp)
  ├── wp-json/iato-mcp/v1/message     ← single JSON-RPC endpoint (tools, incl. `rollback`)
  ├── wp-json/iato-mcp/v1/rollback    ← REST rollback endpoint (same dispatch as the MCP tool)
  ├── class-mcp-server.php            ← MCP protocol handler
  ├── class-auth.php                  ← Application Password validation
  ├── class-oauth.php                 ← OAuth 2.1 server (per-client codes/tokens, PKCE, revocation)
  ├── class-oauth-store.php           ← OAuth tables: registered clients, hashed tokens
  ├── class-iato-client.php           ← IATO REST API HTTP client
  ├── class-seo-adapter.php           ← Yoast / RankMath / SEOPress adapter
  ├── class-change-receipt.php        ← before/after audit trail for writes
  ├── class-cache.php                 ← page cache purges and the `cache` response object
  ├── class-theme-builder.php         ← Elementor Pro's Theme Builder, behind one guarded object
  ├── class-site-image.php            ← the site icon and logo: validation, sizes, Elementor's saved value
  ├── class-post-date.php             ← dates on create_post and update_post, and what they do to the status
  ├── class-url-move.php              ← page parents: the rules, the URLs that move, the receipt, the slug check
  ├── class-permalinks.php            ← permalink structure and bases: what moves, the change, its rollback
  ├── class-redirects.php             ← redirects for moved URLs, created and removed through the redirect plugins
  ├── class-media-chunks.php          ← chunked uploads: sessions in uploads/iato-mcp-tmp
  ├── class-custom-css.php            ← the theme's Additional CSS: who may write it, what is refused
  ├── class-user-profile.php          ← the public fields of a profile, past the save filters
  ├── class-sanitize-report.php       ← what sanitising removed (`sanitized_report`)
  ├── class-element-cache-guard.php   ← keeps Elementor's element cache key and shortcode out of tool calls
  ├── class-inline-markup.php         ← opt-in inline SVG and style blocks in HTML widgets
  ├── class-schema.php                ← migrations, table repair and health
  └── tools/
      ├── wp/        ← WP REST wrappers (posts, SEO, media, menus, taxonomy, Elementor, etc.)
      └── bridge/    ← IATO API → WP-slug-enriched read tools (require IATO API key)
                       |
                       v
                  IATO Platform (iato.ai/api)
```

Authentication: WordPress Application Passwords (WP 5.6+), the plugin's own Bearer key (`iato_mcp_key`), and OAuth 2.1 with PKCE (per-client tokens issued by the plugin since 1.13.0; see "OAuth server" below). See "Token binding" below for which WordPress user each path runs as.
IATO API key: optional, stored in `get_option('iato_mcp_api_key')`, set via Settings > IATO MCP or the Setup Wizard.

**Autopilot / governance / Review Queue are intentionally not part of this release.** They were removed in the v1.0.0 scoping to get a clean MCP server into the WP.org directory. They will return in a future release, designed correctly (async sync, resilient to IATO outages, proper approve→apply→receipt wiring).

## MCP Protocol

JSON-RPC 2.0 over HTTP POST. Three methods:

- `initialize` — return server info and capabilities
- `tools/list` — return all registered tool definitions
- `tools/call` — dispatch to the correct tool handler, return result

All tools return an array with a single `content` item of type `text` containing JSON:
```php
return [
    'content' => [[
        'type' => 'text',
        'text' => wp_json_encode($data),
    ]]
];
```

On error, return `isError: true` with a message — never throw exceptions out of tool handlers. Since 1.14.0 `IATO_MCP_Server::handle_tools_call()` also catches any `Throwable` a handler lets out (another plugin's code, a TypeError): the result is `isError` with JSON text `{error: "tool_exception", tool, exception, message}` (the message says writes made before the failure may have been applied and to check the change receipts), the call log records `tool_exception`, and under `WP_DEBUG` the tool, class, message and file:line go to the PHP error log (`tool_exception_result()`; tests `tests/McpServerCatchTest.php`).

## Coding Rules

- Use `wp_remote_post` / `wp_remote_get` — never curl directly
- Sanitize all option reads: `sanitize_text_field(get_option(...))`
- All tool handlers must return `WP_Error` on failure, never die/exit
- Nonces not used on MCP endpoint (it uses Application Password / OAuth auth)
- Capability check on every write tool: `current_user_can('edit_posts')` minimum
- Admin-only tools (settings, taxonomy write): `current_user_can('manage_options')`. Menu tools need `edit_theme_options`, WordPress's own capability for menus (since 1.10.0): an administrator's by default, and a role plugin can grant it to others
- Object-level check on every write that takes an ID, after the existence check: `IATO_MCP_Auth::require_cap( 'edit_post', $post_id )` (or `delete_post`, `edit_term`, `delete_term`); publishing needs `IATO_MCP_Auth::require_publish_cap( $post_type )`. The site key passes all of these; Application Password users are checked against the object. The per-tool inventory is in the 1.12.1 release notes, kept outside the repository. Since 1.16.0 `require_cap( 'edit_post' | 'delete_post', $id )` refuses a revision for everyone, the site key included (`revision_target`): `update_post_meta()` sends a revision's meta to its parent, and WordPress's `edit_post` lets administrators through. `get_post_meta` asks about the parent instead, so a revision's meta can still be read.
- Update post columns with `IATO_MCP_Auth::update_post_fields( $fields )`, not `wp_update_post()`. `wp_update_post()` runs the whole post through the save filters, and the kses lock keeps those on, so a change to the title removed iframes and scripts from the content. `update_post_fields()` puts every column the call does not set back as stored; `$verbatim = true` stores the given text as it is and allows a post left empty, for rollbacks. `IATO_MCP_Auth::keeping_post_columns( $post_id, $write, $named, $verbatim )` is the same rule around any write that saves a post: `write_pipeline()` (naming `post_content`) and rollback's `wp_trash_post()`. It hooks `wp_insert_post_data` and `wp_insert_attachment_data`, and acts only on `$post_id` and the revision a save makes of it, because a save can start others (a menu item for a newly published page, another plugin's hook). A write that names no text column also skips WordPress's empty-post refusal, which reads the filtered text: a post holding only an iframe would otherwise fail a status change.
- A meta key from a client goes through `IATO_MCP_Meta_Policy::check_stored_key( $post_id, $key )` as well as `check_write()`: the column's collation decides which row a key reaches, and that can be a row with another name (case, accents, trailing spaces, look-alike characters), so the check asks the database (`meta_key_mismatch`, `meta_key_too_long`). A key this post has not got yet would be a new row that later writes of the real key land in, leaving that key reading as empty, so another spelling stored anywhere on the site is enough to refuse it (`CAST(meta_key AS BINARY)`, and only for a new row, because that query reads every row of the key). Known limit: with `force`, a spelling of a key the site does not hold yet still makes its own row. `'0'` is refused because WordPress stores nothing under it. A backslash is refused outright, in `check_write()` too, `force` included (`invalid_meta_key`): `update_metadata()` unslashes the key after these checks have read it. What is allowed matches exactly: another case of an allowed key needs `force`, and `_elementor_` keys must match `ELEMENTOR_WRITABLE` exactly.
- Never rebuild rewrite rules in the request that changes the permalink structure or a base (1.20.0). `WP_Rewrite::init()`, which the setters call, empties the rules and endpoints plugins added on init, and taxonomies keep the old base until the next request. Use `IATO_MCP_Permalinks::apply()`: it empties the stored rules for the next request to build and blocks storing a rebuild for the rest of this one. `flush_rewrite_rules()` stays right for changes that leave the structure alone (`page_on_front`).
- Never write to wp_options without `sanitize_*` on the value
- Slash what you hand to WordPress write functions: `wp_insert_post()`, `wp_update_post()`, `wp_insert_attachment()`, `update_post_meta()`, `wp_insert_term()`, `wp_update_term()`, `wp_update_nav_menu_item()` and `wp_update_user()` expect slashed input and run `wp_unslash()`, so an unslashed value loses every backslash (`C:\Users` becomes `C:Users`, `\"` becomes `"`). Pass `wp_slash( $value )`, arrays included. `update_option()` does not unslash. Live check: `tests/wp-env/backslash-live.sh` (installs Yoast SEO for its run when absent).
- Dry-run mode for destructive write tools: accept `dry_run: true`, return what *would* change
- All files namespaced under `IATO_MCP_` prefix for constants, `IATO_MCP` for classes
- Plugin slug: `iato-mcp`, text domain: `iato-mcp`
- Every IATO API call sends `X-IATO-Plugin-Version` and `X-IATO-Plugin-Capabilities: mcp-read` headers (set in `class-iato-client.php::default_headers()`)

## Schema migrations

`includes/class-schema.php` — `IATO_MCP_Schema`. Table changes and one-shot data fix-ups are keyed by an integer schema version (`iato_mcp_schema_version`, `IATO_MCP_Schema::VERSION`) that is independent of the plugin version. Why: a site that ran a pre-release build already stores that build's `iato_mcp_db_version`, so a `version_compare` gate on the final release would skip every table change made after that build (found during the 1.13.0 staging test). `run()` executes every step above the stored version in order and bumps the option after each one; a step that throws stops the run without advancing past it and is retried on the next request; deleting the option replays everything. Every step must therefore be idempotent (dbDelta, `INSERT IGNORE` / `NOT EXISTS`, option writes that tolerate repeats). Steps so far: 1 base tables (receipts, call log, media phase log), 2 OAuth client/token tables + carry-over of the option-based clients + legacy flags, 3 OAuth grants table + backfill, 4 receipt actor columns (`actor_*`, `rolled_back_by_*`, index on `actor_user_id`) and call-log `credential_kind` / `client_id`, 5 receipts `pruned_at` and index `target_applied (target_type, applied_at)` for the retention job, 6 Elementor's element cache refreshed (`IATO_MCP_Element_Cache_Guard::refresh()`), 7 tables repaired and checked (`IATO_MCP_Schema::repair()`; see "Undo records and table health"). `run()` is called from `iato_mcp_maybe_run_migrations()` on `plugins_loaded` and from activation. The tool-list backfill (`TOOL_MIGRATION_BACKFILL`) stays keyed by the plugin version, which is only bumped afterwards.

**Adding a step** (whenever a change touches tables): append `N => [ self::class, 'step_name' ]` to `steps()` with `N = VERSION + 1`, bump `VERSION`, make the step idempotent, and add a case to `tests/wp-env/schema-migration-live.sh`. `tests/SchemaMigrationTest.php` checks ordering, no-op reruns, the stop-on-failure rule and that the step map is contiguous.

## Release Checklist (adding or removing tools)

When adding a new MCP tool, three edits must land together — missing any of them produces a tool that exists in code but is invisible on upgraded installs (the bug class that produced the v1.3.0 → v1.3.1, v1.4.0 → v1.4.5, and v1.6.0 → v1.6.1 follow-up patches):

1. Register the handler with `IATO_MCP_Server::register_tool()` in the appropriate `includes/tools/wp/tool-*.php` or `includes/tools/bridge/tool-*.php` file.
2. Append the tool name to the `TOOL_NAMES` constant in `includes/class-settings.php`, plus a matching entry in `TOOL_DESCRIPTIONS` and a category placement in `TOOL_CATEGORIES`.
3. Append the tool name to `IATO_MCP_Settings::TOOL_MIGRATION_BACKFILL` under a gate equal to the release version it ships in. `iato_mcp_maybe_run_migrations()` walks this map once on upgrade and appends any missing names to the saved `iato_mcp_tools` option, so upgraded installs see the new tool the next time they make any request.

4. Append a write tool to `IATO_MCP_Cache::WRITE_TOOLS` in `includes/class-cache.php`, so it carries a `cache` object even when it changes nothing. `tests/CacheResponseTest.php` fails for a tool that is neither listed nor named like a read (`get_`, `list_`, `find_`, `search_`, `resolve_`). The tool must declare and honour `dry_run` (`tests/DryRunContractTest.php`): `run_tool()` refuses a truthy `dry_run` with `dry_run_unsupported` for any tool that does not declare it, reads included, so a tool with side effects (`start_iato_crawl`, `get_iato_suggestions`) cannot run when asked for a preview.
5. List every argument the handler reads in `inputSchema`, and read every property listed. `tests/ToolSchemaParityTest.php` (1.19.1) loads every tool file in a fresh process and compares each registered schema with the keys its handler reads, found from source by `tests/tool-arg-reader.php`: `$args['key']`, `array_key_exists( 'key', $args )`, `$args[ $x ]` inside a `foreach` over a literal list or a class constant, and `$args` handed whole to the plugin's own functions and static methods, followed under its parameter name there. Names kept for IATO's Autopilot (`post_id` for `id`) go in its `ALIASES`; a read the reader cannot follow fails until it is made plain or explained in `UNDERSTOOD`. Nested object properties are not compared.
6. When a tool gains an argument, check the server instructions (`iato_mcp_build_server_instructions()` in `iato-mcp.php`) for text that lists that tool's arguments. The Elementor section lists the fields `update_post` may change there, and it stayed at `status, title, excerpt` until 1.19.3. `tests/ServerInstructionsTest.php` (1.19.3) builds the instructions with each combination of page builders active and checks that every field the list names is in `update_post`'s schema. It does not notice a field missing from the list.

Step 3 is the one that historically gets missed. The backfill map lives next to `TOOL_NAMES` in the same file specifically so a reviewer can eyeball the two lists side-by-side and confirm parity. Adding a new tool without a matching backfill entry is the failure mode; the loop walker in `iato-mcp.php` handles every other detail.

Removing a tool is the reverse: take it out of `TOOL_NAMES` and from any category placement; leave `TOOL_MIGRATION_BACKFILL` alone (historical entries are still correct).

## Release Checklist (adding a new admin setting)

When adding a new option to the Settings page, three edits must land together — missing any of them produces a setting that renders in the UI but silently discards on save (the bug class that produced the v1.7.0 → v1.7.1 follow-up patch):

1. Register it with `register_setting()` in `IATO_MCP_Settings::register_settings()` using the shared `OPTION_GROUP` constant. The sanitize_callback runs through both `options.php` and admin-ajax persistence paths.
2. Render the input in `IATO_MCP_Settings::render_page()` with a `name="..."` attribute that exactly matches the option key passed to `register_setting()`. The field must live inside the `<form method="post" action="options.php">` opened at the top of the General tab. For checkboxes, emit a hidden `<input type="hidden" value="0">` sibling with the same name so unchecked state still POSTs the key.
3. Wire the corresponding `$_POST` → sanitize → `update_option()` line into `IATO_MCP_Settings::ajax_save_settings()`. This is the step that historically gets missed: the form is hijacked through admin-ajax (some hosts 503 on options.php POSTs due to upstream WAF / timeout rules), so the `register_setting()` allowlist never gets a chance to apply. The AJAX handler hardcodes the keys it persists — anything not explicitly handled there is silently dropped.

Step 3 is the trap. The AJAX handler lives directly above `ajax_test_api_key()` in `class-settings.php`; co-locate any new field's persistence line there alongside its peer registrations so a reviewer can eyeball the two lists side-by-side.

`get_post` accepts an opt-in `include_shadowing: true` parameter that attaches `is_shadowed_by` when an Elementor Theme Builder template overrides the slug-based render. Default is off so the hot path stays fast.

`get_elementor_data` accepts a `format` parameter (`raw` | `compact` | `summary`). All v2 reads include a `revision` hash for use with `if_revision` guards on writes.

`update_post` accepts a `slug` parameter alongside title/content/excerpt/status. Slug input is strictly validated (lowercase a-z/0-9/hyphens, no leading/trailing/double hyphens, max 200 chars, must round-trip through `sanitize_title()` unchanged) and conflicts return `slug_conflict` rather than auto-suffixing. Changing the slug of a non-draft post additionally requires `confirm_url_break: true` since it breaks inbound links. `create_post` and `update_post` responses include a `notice` field on builder-driven sites (Elementor / Divi / WPBakery / Beaver Builder) — on Elementor it tells the agent to fetch a reference post and use the Elementor widget tools; on the others it tells the agent the layout must be finished in WP admin. The `notice` field is absent on Gutenberg-only sites.

`rollback` reverses a prior write by `change_id`. Any write tool that returns a `change_receipt` (or `change_receipts[]`) can be undone in one MCP call — Claude passes the `change_id` back to `rollback`, which validates the stored before_value, dispatches by `target_type`, and marks the receipt rolled-back so it cannot be re-applied. Wraps `IATO_MCP_Rollback::rollback_by_id` (the same dispatch path used by the REST endpoint at `wp-json/iato-mcp/v1/rollback`). Receipt `target_type` values: `post`, `page`, `image`, `menu_item`, `taxonomy`, `redirect`, `elementor_widget`, `elementor_atomic` (1.14.0, one Atomic Editor element's settings; see "Elementor Atomic (Editor V4) writer"), `post_meta`, `attachment`, `site_setting` (1.15.0, `update_site_settings`; the option name in `field`, limited to `IATO_MCP_Rollback_Conflict::SITE_OPTIONS` and `SITE_THEME_MODS`), `menu` and `menu_location` (1.17.0; see "Menus and theme locations"), `elementor_template` (1.17.0; see "Theme Builder templates"), `custom_css` and `user_profile` (1.19.0), `permalinks` (1.20.0; see "Page parents and permalinks"). `update_post` records one receipt per changed field (`title`, `content`, `slug`, `excerpt`, `status`), and `page_attributes` for a new parent or menu order (1.20.0); `create_post` records `target_type=post, field=create` and rolls back via `wp_trash_post`. `update_post_meta`, `set_page_settings`, and `set_featured_image` all record under `target_type=post_meta` with the meta key in `field` — rollback restores the previous value or deletes the key if `before_value` was null. `create_media` records `target_type=attachment, field=create` and rolls back via `wp_delete_attachment(force=true)` (the underlying file is removed).

**Receipt actors, the rollback rule and the conflict check (1.13.0, schema step 4).** `IATO_MCP_Change_Receipt::record()` stores who made the change: `actor_user_id`, `actor_kind` (`site_key` | `oauth` | `application_password`, or `wordpress` outside an MCP request) and `actor_client_id` (OAuth), from `IATO_MCP_Auth::credential()` via `current_actor()`; every returned receipt carries `actor` (`describe_actor()`: user id, login, kind, client id and name). `mark_rolled_back()` stores `rolled_back_by_*` the same way. Before schema step 4 has run (`has_actor_columns()`), receipts are written without these columns rather than lost. `IATO_MCP_Rollback::check_permission()` (tool and REST route) keeps the 1.12.1 object-level checks and then, for a receipt with an actor, requires the same WordPress user or `manage_options` (`require_cap()`, so the unbound key, a bound key and OAuth tokens, whose users are administrators, always pass); otherwise `rollback_actor_mismatch` (403). Receipts without an actor (recorded before 1.13.0) keep the object rules alone. `IATO_MCP_Rollback::execute()` is the shared core: already-rolled-back (names who), `preflight()` (Elementor receipts that hold only a hash, `update_term` receipts without a term id → `rollback_unavailable`), `IATO_MCP_Rollback_Conflict::check()` (`includes/class-rollback-conflict.php`: one reader per target_type/field returns the current value in the form the receipt recorded; canonical comparison treats '' as null, decodes JSON, ignores key order and scalar types; creates conflict when the object was modified after `applied_at`, deletes when the object is back; redirects of handlers whose rules the plugin cannot read, unknown fields and missing objects are `unverifiable` and proceed), refusal `rollback_conflict` (409, `conflict_check` with `current_value` / `expected_value`) unless `force: true`, `dry_run: true` (reports `would_roll_back`, `would_restore`, the check; writes nothing), dispatch, mark. The `rollback` tool returns refusals that carry details (`rollback_conflict`, `rollback_actor_mismatch`, `rollback_unavailable`, `already_rolled_back`) as an isError result whose text is JSON (`iato_mcp_rollback_error()`), because MCP clients see only the text. For the check to hold, record sites store what was actually written, read back with the reader the check uses: `update_post` / `create_post` (WordPress filters titles and content on save), `update_seo_data`, `update_canonical`, `update_alt_text`, `update_menu_item_details` (`IATO_MCP_Rollback_Conflict::menu_item_value()`); `update_term` snapshots carry `term_id`. Elementor receipts (`elementor_widget`) store the pre-write `_elementor_data` text as `before_value` (one full copy per edit; responses keep the slim receipt) and the stored revision hash as `after_value`; rollback restores the text through the `post_meta` path (`write_elementor_meta()`), reports `restored_revision` instead of the tree, and when the post had no Elementor data before `update_elementor_data` the before value is an envelope (`IATO_MCP_Rollback::no_elementor_envelope()`: a JSON object with the original `post_content` and builder flag; trees are JSON arrays) whose rollback removes `_elementor_data`, restores the flag and writes the original content back verbatim (`restore_post_content()`: `wp_slash()`, kses lock lifted and core's kses content filters removed for that write, both restored in `finally`). Taxonomy `assign` / `terms` rollbacks take the taxonomy from any term in the receipt (`taxonomy_of_ids()`), after IDs included. The REST route accepts `force` and `dry_run` too and still requires the caller's `before_value` to equal the stored one (for Elementor receipts that is the whole tree). Tests: `tests/RollbackActorConflictTest.php` (stubs in `tests/stubs-actor.php`); live: `tests/wp-env/rollback-actor-live.sh` → `.py` (mints an OAuth access token straight into the tables; `--cleanup`) and `tests/wp-env/rollback-plugins-live.sh` → `.py` (installs Yoast SEO, Safe Redirect Manager and Redirection for the run; `--cleanup` uninstalls them). Known limits: a created redirect cannot be rolled back on any handler, and with Redirection no redirect receipt has a before value (the plugin cannot read Redirection's rules), so none can be rolled back.

**Receipt retention (1.13.0, schema step 5).** `includes/class-receipt-retention.php` (`IATO_MCP_Receipt_Retention`): Elementor receipts hold a full copy of the page, so a daily WP-Cron event (`iato_mcp_prune_receipts`, scheduled on `init` when missing, cleared on deactivation and in `uninstall.php`) sets `before_value = NULL` and `pruned_at` on `elementor_widget` receipts older than the retention period, in `UPDATE … LIMIT 200` batches within a 10-second budget. The receipt row stays as an audit record. Period: filter `iato_mcp_receipt_retention_days` (default 90; 0 or less keeps every copy). WP-Cron only runs on visits and can be disabled, so `IATO_MCP_Change_Receipt::record()` calls `maybe_run_overdue()`: when the last run (option `iato_mcp_receipt_prune_last`) is more than two days old, one batch runs on `shutdown` of that request. `IATO_MCP_Rollback::preflight()` refuses a receipt with `pruned_at` (`rollback_unavailable`, pointing at Elementor's revisions) before anything else, so an emptied before value is never read as "the post had no Elementor data". Diagnostics shows the period, the last run and the next one. Tests: `tests/ReceiptRetentionTest.php` (cron stubs in `tests/stubs-cron.php`); live: `tests/wp-env/receipt-retention-live.sh` (test-only mu-plugin `tests/wp-env/mu-receipt-retention-test.php` sets the filter from an option).

The `initialize` response advertises `capabilities.elementor.v2: true` when Elementor is active, plus `capabilities.rollback: true` always — clients can feature-detect without a `tools/list` round-trip.

`create_media` accepts `defer_subsizes: true` (default false) which schedules `wp_generate_attachment_metadata` via WP-Cron instead of running it inline. The response returns immediately with the attachment ID and canonical URL; intermediate sizes appear on the next cron tick. Recommended whenever the call goes through a managed MCP gateway with a request timeout (Anthropic's gateway times out around 30s) — sites with image-optimisation plugins routinely push synchronous metadata generation past that limit. Per-phase timing logs are emitted to PHP's error log under the prefix `[iato-mcp create_media:<req_id>]` for live diagnosis when a call hangs or fails.

`update_elementor_data` goes through the shared write pipeline (see "Elementor write pipeline and sanitising"), records an `elementor_widget` receipt (`elementor:document:replace`), turns Elementor on for a post with no data or, with `activate_builder: true`, for one with Elementor turned off (see "Pages with Elementor turned off"), and accepts `inherit_settings_from: <post_id>` (and optional `inherit_keys: string[]`, limited to allowlisted `_elementor_` keys) to clone a curated set of theme/builder per-post overrides from a source post in the same call. The default key list spans Astra (`site-post-title`, `site-sidebar-layout`, `site-content-layout`, `site-content-style`, `site-sidebar-style`, `ast-main-header-display`, `ast-global-header-display`, `ast-banner-title-visibility`, `ast-breadcrumbs-content`, `ast-featured-img`, `footer-sml-layout`), WordPress (`_wp_page_template`), and Elementor (`_elementor_page_settings`, `_elementor_template_type`). Empty source values are copied through (Astra stores meaningful state as empty strings). Keys that already match between source and target are reported in `inherited_skipped[]` with `reason: 'noop'`.

## Token binding (who an MCP request runs as)

`includes/class-auth.php` — `IATO_MCP_Auth::authenticate()` is the `permission_callback` for `/iato-mcp/v1/message` and `/iato-mcp/v1/rollback`, and the single place the current user is set for Bearer requests.

| Credential | Runs as | `require_cap()` |
|---|---|---|
| Bearer key bound to an owner (`iato_mcp_key_owner` > 0) | the owner, via `wp_set_current_user()` after re-checking on every request that the user exists and holds `manage_options` (else 403 `iato_mcp_owner_missing` / `iato_mcp_owner_demoted`, logged once per request in the call log with `rpc_method: auth`) | `user_can( $owner, $cap )` — real |
| Bearer key with no owner (issued before binding existed) | user 0, exactly as before binding | `true` for any cap; `require_bound_user()` returns `iato_mcp_token_unbound` for features that need a user |
| OAuth access token (`Bearer iato_at_…`, 1.13.0) | the administrator who approved the connection, via `wp_set_current_user()` after the same exists + `manage_options` re-check (else 401 `iato_mcp_unauthorized`; a missing or demoted user also revokes the grant and is logged with `error_code: iato_mcp_token_user_missing` / `_demoted`). Expired and revoked tokens are 401 with `error="invalid_token"` in `WWW-Authenticate`. OAuth connections made before 1.13.0 hold the site key and arrive on the Bearer-key rows above. | `user_can( $user, $cap )` — real |
| Application Password (Basic) | the real user, set by WP core | `user_can( $user, $cap )` |

- **Owner record.** `iato_mcp_key_owner` is written only through `IATO_MCP_Auth::bind_key_owner()`: `maybe_generate_key()` (activation; WP-CLI activation has no user, so the key stays unbound), `rotate_key()` (Regenerate binds to the regenerating admin), and the Settings "Token owner" control (`admin_post_iato_mcp_assign_key_owner`, admins only). OAuth consent bound an unbound key to the approving admin in 1.12.x; since 1.13.0 consent issues the client its own token and never touches the key. The token format, storage and validation are unchanged.
- **kses stays on for every MCP request (1.13.0).** `authenticate()` attaches a `map_meta_cap` filter that returns `do_not_allow` for `unfiltered_html` and `edit_css` for the rest of the request (before `wp_set_current_user()` for the bound key and OAuth tokens; followed by `kses_init()` on the Application Password path, where core had already decided its filters), so WordPress' content filters stay active and Elementor's `Document::save()` applies `kses_post_deep`. Application Password users keep `unfiltered_html` only when the `iato_mcp_allow_unfiltered_html` filter (`$allow, $user_id, $kind`) returns true and they hold the capability; the decision is taken once in `authenticate()` and read through `IATO_MCP_Auth::unfiltered_html_allowed()`. Create/update_post additionally run `wp_kses_post` themselves. The lock is lifted (`IATO_MCP_Auth::write_unlocked()`, restored in `finally`) around Elementor's `Document::save()` and around the plugin's own `_elementor_` meta writes, so Elementor's blanket `kses_post_deep` and its REST `sanitize_callback` on `_elementor_data` do not strip values the request did not change; the plugin's diff pass has already sanitised the changed leaves. The lift only removes the plugin's filter: a user who does not hold `unfiltered_html` (an Author's Application Password) still lacks it inside the save. For an unbound legacy key (user 0) the lift has nothing to show through, so the plugin's own `_elementor_` meta writes additionally run inside `IATO_MCP_Elementor_Adapter::without_elementor_meta_sanitizing()` (from 1.12.2): it removes every callback on the `sanitize_post_meta__elementor_data` / `_elementor_page_settings` hooks (and their `_for_<post_type>` variants) for the write and restores them in `finally`, logging each one under `WP_DEBUG`. `IATO_MCP_Elementor_Adapter::write_elementor_meta()` combines the two and is what the pipeline's fallback write, rollback, `update_post_meta`, `set_page_settings` and inherit use for Elementor keys.
- **What changes with a bound owner.** New posts, media, menu items and revisions get the owner as author (was 0). Elementor's `Document::save()` now runs for Bearer requests (it refused user 0), so `post_content` is Elementor's rendered HTML rather than the frontend fallback, and `_elementor_data` is re-encoded by Elementor; the write pipeline reports `elementor_save: true|false|'error'` (guarded with `Throwable`) and checks persistence structurally (`same_element_tree()`) instead of by byte length. The owner's own edit lock no longer blocks writes. `tax_input` on insert is honoured. Bound Bearer behaviour equals today's Application Password admin behaviour except for the kses lock.
- **Inline markup (1.15.0).** The opt-in in "`sanitized_report` and the inline markup opt-in" reads the capability inside `write_unlocked()` and widens one value's allowed tags. The lock itself does not change.
- **Legacy keys.** Nothing binds automatically on upgrade. An unbound key shows an admin notice (`key_owner_notice`, `manage_options`, dismissible per user except on the plugin's Settings page) and an "Unassigned (legacy mode)" badge in the Token owner row; Diagnostics shows the owner state.
- **Multisite** is not declared. An owner who is not a member of the site has no capabilities there and is rejected as demoted.
- Tests: `tests/AuthBindingTest.php` (stubs in `tests/stubs-auth.php`); live: `tests/wp-env/tools-snapshot.{sh,py}` (before/after behaviour snapshot over Bearer and App Password), `tests/wp-env/mu-manage-elements-probe.php` (test-only mu-plugin calling `elementor/manage-elements` inside a Bearer request).
- `IATO_MCP_Auth::credential()` reports the credential kind (`site_key` | `oauth` | `application_password`), the user id and, for OAuth, `client_id` / `grant_id`, for receipts and logs.

## OAuth server

`includes/class-oauth.php` (`IATO_MCP_OAuth`) + `includes/class-oauth-store.php` (`IATO_MCP_OAuth_Store`). Follows the MCP authorization specification revision 2026-07-28 (OAuth 2.1, RFC 8414 / 9728 metadata, RFC 8707 `resource`, RFC 9207 `iss`, RFC 7591 registration, RFC 7009 revocation). Routes are matched on `init` priority 1 from `REQUEST_URI` (so they work on any permalink setting): `/.well-known/oauth-protected-resource[/…]`, `/.well-known/oauth-authorization-server`, `/oauth/register`, `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`.

- **Credentials.** Code: 43-char random, single use, 5 min, bound to client, redirect URI, PKCE challenge and approving user. Access token `iato_at_…`, 1 h. Refresh token `iato_rt_…`, 30-day sliding, rotated on every refresh. Absolute grant lifetime 180 days from consent (`iato_mcp_oauth_grant_lifetime` filter, 0 disables), after which refresh returns `invalid_grant`. Everything is stored as SHA-256 in `{prefix}iato_mcp_oauth_tokens`; one row per authorization in `{prefix}iato_mcp_oauth_grants` (`grant_id`, client, user, redirect URI, `granted_at`, `revoked_at`, `revoked_reason`). The site key is never issued or accepted by any OAuth endpoint.
- **Grant row is the authority.** Every revocation path (Revoke, Disconnect all, `/oauth/revoke`, code replay, refresh reuse, approver missing/demoted/deleted, the 180-day limit) sets `grants.revoked_at` (+ reason) through `IATO_MCP_OAuth_Store::revoke_grant()` / `revoke_all_grants()` / `revoke_user_grants()`; `find_token()` joins the grant, and the token endpoint, the refresh path and `authenticate()` refuse any token whose grant is revoked, whenever the token row was created. Codes and refresh tokens are claimed atomically: `mark_used()` is one `UPDATE … WHERE used_at IS NULL` and returns the affected rows; 0 means another request consumed it first (replay / reuse → the grant is revoked, `invalid_grant`). A code or refresh token is spent on first presentation, success or failure. `backfill_grants()` (schema step 3) derives grant rows for sites that ran the first 1.13.0 build.
- **Registration** (`{prefix}iato_mcp_oauth_clients`): at most 10 redirect URIs, each `https`, or `http` to `localhost` / `127.0.0.1` / `[::1]` (matched port-agnostically at authorize time for Claude Code's ephemeral port; same host string, same path and query); `client_name` stored (≤100 chars); public clients only; a failed insert is a 500 `server_error`; limits 10 per IP per 10 min and 100 per site per hour via transients (`iato_mcp_oauth_registration_limits` filter; `REMOTE_ADDR` as the call log uses it, so behind a proxy the IP bucket is effectively site-wide); clients never authorized within 24 h, or authorized but without a live grant for 30 days, are pruned lazily on registration.
- **Authorize.** Not logged in → wp-login and back (`login_return_url()`: site origin + `REQUEST_URI`, so subdirectory installs are not doubled); logged in without `manage_options` → a 403 page (`wp_die`), not a login loop. Unknown client or unregistered redirect URI → JSON 400 (never a redirect); afterwards protocol errors (`unsupported_response_type`, missing/non-S256 PKCE including a missing `code_challenge_method`, bad `resource`) go back to the client by redirect with `error`, `state`, `iss`. The consent form's nonce action is `consent_nonce_action()` (hash of client_id, redirect_uri, code_challenge), so a nonce rendered for one request cannot approve another. `resource` is normalised (scheme/host case, default port, trailing slash) and must equal `rest_url('iato-mcp/v1/message')`; an `https` resource is accepted for an `http` canonical URL (TLS-terminating proxy) and logged as `oauth` / `resource_scheme_upgrade`, never the reverse. Consent shows client name, redirect host (loopback warning), registration time and the approver; Deny is a POST that redirects with `access_denied`. Approval writes the code row, marks the client authorized and logs `oauth` / `grant`. Consent does not touch the site key.
- **Token endpoint** accepts form-encoded and JSON. `authorization_code` → PKCE via `verify_pkce()` against the code row, `resource`, approver re-check, then an access + refresh pair. `refresh_token` → client match, rotation/reuse detection, expiry, absolute lifetime, approver re-check. Refusals are `invalid_grant` (what Claude needs to re-authorize) or `invalid_target`.
- **Revocation.** `POST /oauth/revoke` (`token`, optional `client_id`; either token of a grant revokes the grant; always 200). Settings card "Connected OAuth clients" (`render_oauth_clients_card()`, after the settings `</form>` so its per-row POST forms do not nest; `admin_post_iato_mcp_oauth_revoke` with a per-grant nonce; "Disconnect all" posts `admin_post_iato_mcp_oauth_revoke_all`, revokes every live row including pending codes and reports the number of connections). `deleted_user` revokes that user's grants. Regenerate leaves OAuth grants alone. Every revocation is logged (`oauth` / `revoke`, `request_args.reason`: endpoint, admin, admin_all, code_replay, refresh_reuse, grant_lifetime, user_missing, user_demoted, user_deleted). Routine refreshes are not logged.
- **Migration (1.13.0).** Schema steps 2 and 3 (`IATO_MCP_Schema`, see "Schema migrations"): tables created, clients from the retired `iato_mcp_oauth_clients` option copied over as authorized, the `iato_mcp_oauth_pkce` transient deleted, grant rows backfilled. Sites that had OAuth clients get two flags: `iato_mcp_oauth_legacy_notice` → `IATO_MCP_Settings::oauth_legacy_notice()` (site-wide dismiss hides the notice only) and `iato_mcp_oauth_legacy_key` ("pre-1.13.0 connections may still hold the key"), which drives the Settings card hint and the Diagnostics badge and is cleared only by `IATO_MCP_Auth::rotate_key()` (Regenerate clears both). Pre-1.13.0 connections hold the site key and keep working through the Bearer path; reconnecting the client moves it to its own token; regenerating the key cuts them all.
- **Not built:** Client ID Metadata Documents (`client_id_metadata_document_supported` is deliberately absent, so Claude uses dynamic registration). Subdirectory installs: the spec's path-aware well-known URLs sit at the host root and do not reach WordPress; the `WWW-Authenticate` `resource_metadata` pointer is the working discovery path there.
- Tests: `tests/OAuthFlowTest.php`, `tests/AuthOAuthTokenTest.php`, `tests/OAuthPkceTest.php` (in-memory store and WP stubs in `tests/stubs-oauth.php`); live: `tests/wp-env/oauth-live.sh` → `oauth-live.py` (metadata, registration rules and limits, consent incl. the 403 page and nonce binding, codes, tokens, grant-level revocation, 20 parallel refreshes, refresh, expiry by backdating rows, revocation through the endpoint and the Settings forms, demoted/deleted approver, loopback, pruning, legacy-key flag and Regenerate, site-key sweep).

## WordPress Abilities Bridge

`includes/class-abilities.php` — `IATO_MCP_Abilities`. Registers the eleven read-only bridge tools as `iato/*` abilities through the core Abilities API (WordPress 6.9+) so any MCP server built on the WordPress MCP Adapter, and the `wp-abilities/v1` REST API, can discover and run them. `start_iato_crawl` and every write tool are deliberately not registered.

- **One implementation.** `IATO_MCP_Server` keeps a `$catalog` of every tool passed to `register_tool()` (definition + handler), separate from `$tools` (what `tools/list` exposes). Each ability's `execute_callback` calls `IATO_MCP_Server::invoke_tool()`, which runs the same closure the MCP tool uses and unwraps the `ok()` text envelope. `WP_Error`s pass through with array messages JSON-encoded, exactly as `handle_tools_call()` does, so both surfaces return identical text.
- **Catalog-only loading.** `iato-mcp.php` loads the bridge tool files when an IATO key is set (as before) *or* when abilities exposure is on; in the second case `IATO_MCP_Server::set_catalog_only(true)` wraps the requires so nothing is added to `tools/list`. An unconnected site therefore still registers the abilities, and executing one returns `iato_not_connected` with instructions.
- **Names, labels, descriptions** live in `IATO_MCP_Abilities::ABILITIES` (slug → tool, label, description). Descriptions are written for discovery (≤ 400 chars, crawl source + question answered + when to use). Input schemas are derived from the tool's `inputSchema` (`type: object`, `default: []`; nothing is added: since 1.19.1 `get_iato_sitemap` lists `crawl_id` itself). `output_schema` is `{type: object}`.
- **Permissions.** `permission_callback` is `current_user_can( IATO_MCP_Abilities::capability_for( $slug ) )`: `manage_options` for all eleven by default, lowerable per ability with the `iato_mcp_ability_capability` filter (`function( string $cap, string $ability, string $tool ): string`). The filter is evaluated on every call, not captured at registration. Abilities run as the REST-authenticated WordPress user; `IATO_MCP_Auth::require_cap()` is not involved. Every IATO call uses the stored API key only.
- **Meta.** `public`, `show_in_rest`, `mcp.public` all `true`; annotations `readonly: true, destructive: false, idempotent: true` (`DEFAULT_ANNOTATIONS`), except `get-suggestions`, which is only `destructive: false` because it can trigger suggestion generation on IATO (a per-entry `annotations` override in the table). Non-readonly abilities run over POST on core's `wp-abilities/v1` route. The MCP Adapter decides exposure from `meta.mcp.public`; core REST from `meta.show_in_rest`.
- **Setting.** `iato_mcp_abilities_enabled` (boolean, default on, "IATO Platform" card, admin-ajax persisted per the settings checklist). Off → no hooks are attached and no `iato/` abilities exist. The per-tool toggles in the Tools card are honoured too: a tool switched off disappears from both surfaces.
- **Hooks.** `IATO_MCP_Abilities::init()` runs on `plugins_loaded` and attaches `wp_abilities_api_categories_init` / `wp_abilities_api_init` (both fire lazily on first registry access after `init`). Every entry point is guarded with `function_exists('wp_register_ability')`, so WordPress below 6.9 is a silent no-op.
- **Per-tool selection and the bridge tools.** While no IATO key is set, the Tools card renders the twelve bridge tools as disabled checkboxes, and browsers never submit disabled inputs. `includes/tools-selection.php` (pure functions) keeps that from switching them off: the card also emits a hidden `iato_mcp_tools[]` input for each gated tool that is currently on, `ajax_save_settings()` merges the posted list with the previous state for gated tools (`iato_mcp_merge_gated_tools()`, using the key as it was before the save), `sanitize_tools()` does the same on the options.php path, and `iato_mcp_maybe_run_migrations()` runs a one-shot repair (`iato_mcp_repair_bridge_tools()`: a non-empty list with none of the twelve gets all twelve; flag option `iato_mcp_bridge_tools_repaired`). With a key present the checkboxes are live and an unchecked bridge tool is a deliberate choice that is honoured, including across later gated saves. Tests: `tests/SettingsToolsTest.php`, `tests/wp-env/tools-settings-save.php`.

Tests: `tests/AbilitiesRegistrationTest.php` (loads the production bridge files in catalog-only mode; stubs in `tests/stubs-abilities.php`), `tests/wp-env/abilities-smoke.sh` (three-way parity: core REST run, adapter `execute-ability`, IATO `tools/call`), `tests/wp-env/abilities-settings-save.php` (admin-ajax save path).

## Elementor write pipeline and sanitising

`IATO_MCP_Elementor_Adapter::write_pipeline( $post_id, $elements, $previous_revision, $stored_elements = null )` is the single write path for `update_elementor_widget`, `update_elementor_patch`, `update_elementor_widgets_bulk`, `set_heading_level`, `set_widget_setting` and (since 1.13.0) `update_elementor_data`. Order: (0) unless `IATO_MCP_Auth::unfiltered_html_allowed()`, `IATO_MCP_Elementor_Sanitizer::diff_tree()` compares the new tree with the stored one element by element (matched by id) and sanitises only leaves that differ; (1) cache clears; (2) Elementor's `Document::save()` with the (sanitised) tree, inside `write_unlocked()` and guarded with `Throwable`; (3) only when that returned anything but `true` (refused = user may not edit, e.g. unbound key as user 0; threw = addon controls; Elementor absent) the plugin writes `_elementor_data` itself, so an unsanitised tree is never on disk; (4-6) frontend fallback render, structural persistence check (`same_element_tree()`, ids only), revision. Since 1.13.1, `write_pipeline()` takes `$opts['atomic_ids']` (the atomic elements the write changed): whenever Elementor's save did not store the tree (threw, was skipped for unregistered types, or was refused, as for user 0), every node carrying a changed id (copies included) runs through Elementor's per-element save transform (`atomic_validation_error()` → `validate_element_for_save()`, injectable with `set_element_validator()`); if one fails, nothing is written (`atomic_invalid_settings`). Otherwise the fallback stores the tree; when Elementor's message was `Settings validation failed`, another element on the page is what it rejected and the result lists `invalid_elements`, so a damaged page can be repaired one element at a time. Dry runs (`do_update_widget()`, `update_elementor_patch`, `update_elementor_data`) run the same check and return the same refusal. `update_elementor_data` and `update_elementor_patch` share the whole-tree guard `check_atomic_tree()`; `tree_changes()` treats an element whose type changed as new (every setting checked), and an element whose id appears more often than on the stored page (a copy) like the read flag does: values stored without their typed wrapper are refused, null values and non-schema keys pass. Single-element tools (`do_update_widget()`) validate only the node at the edited JSON pointer path (`$opts['atomic_paths']`); the whole-tree tools validate every node carrying a changed id (`atomic_ids`). Also since 1.13.1, before Elementor's save the pipeline walks the whole tree for element types Elementor cannot load right now (`unregistered_element_types()`: `widgets_manager->get_widget_types()` for widgets, `elements_manager->get_element_types()` otherwise, Elementor's own `Elements_Manager::get_element()` rule; injectable with `set_type_checker()`): `Document::save()` silently drops such elements (a deactivated addon's widgets, atomic elements while the Atomic Editor is off; `document.php:1111-1115`). When any is found, Elementor's save is skipped and the plugin stores the tree itself (step 3, change-only sanitised): `elementor_save: "skipped"`, `skipped_reason: "unregistered_element_types"`, `unregistered_element_types` (`[{type, element_ids}]`), `cache_cleared` (post CSS, element cache, atomic styles, cleared after the frontend render) and `verification` (`verify_untouched()`: element counts, untouched elements identical). Dry runs report the same skip through `preview_report()`. Rollback never calls `Document::save()` (it writes `_elementor_data` directly), so it keeps such elements unchanged. The result carries `elementor_save` (`true|false|'error'|null`), `stored_by` (`elementor|plugin`), and `sanitized: true` + `sanitized_paths` (`<element id>/settings/<path>`, capped at 50) only when a value was altered; `pipeline_report()` copies those onto tool responses and `sanitize_preview()` gives dry runs the same keys.

`includes/class-elementor-sanitizer.php` sanitises by value shape, not widget name, so unknown and addon widgets follow the same rules: URL fields (`url`, `destination`, `href`, `*_url`, and atomic `{$$type: url}` envelopes) → `esc_url_raw` (Elementor's `Url_Prop_Type::sanitize_value()`); `custom_css` (classic, page settings; atomic `styles[].variants[].custom_css.raw`, base64) → `sanitize_textarea_field` (Elementor's `Style_Parser::sanitize_custom_css()`); strings containing `<` → `wp_kses_post` (what Elementor's `Document::save()` applies to every string for users without `unfiltered_html`); everything else verbatim (kses would turn `&` into `&amp;`, double-encoded by widgets that escape on output). Structure keys are never touched. The three functions are injectable (`set_functions()`) for unit tests; `_elementor_page_settings` writes go through `diff_settings()` via `IATO_MCP_Meta_Policy::sanitize_elementor_value()`.

Because the lock is lifted around `Document::save()`, Elementor's own `kses_post_deep` (whole document) does not run for bound-key and OAuth requests; the diff pass is the sanitiser for classic widgets on both paths. Elementor's per-prop atomic sanitising (URL, HTML wrapper tags, `custom_css`) still runs inside its props parser regardless of capability, and its content-sanitizer module still applies to non-`manage_options` users.

**Tree shape (1.16.0).** `IATO_MCP_Elementor_Adapter::tree_shape_error()` refuses what crashes the page for every visitor while Elementor's save reports nothing wrong: a tree with named keys, a node that is not an object, no `elType`, a widget with no `widgetType`, `settings` that are not an object (`null` included). It also refuses a non-scalar `id`. Limited to what was seen to break Elementor 4.3.5, so an element with no `id` or an unknown type stays allowed, as do `elements` with gaps in their numbering. `update_elementor_data` and `update_elementor_patch` check it before their dry runs (`elementor_invalid_tree`, in `DETAILED_ERRORS`), single-widget dry runs and `IATO_MCP_Elementor_Atomic_Writer::apply()` check the page they would store, and `write_pipeline()` is the backstop, except with `verbatim`. Known limit: this is the tree's shape, not each widget's settings. A value of the wrong type for its control (an array as a heading's `title`) can still break a page; rollback recovers it. Because a render can still throw, `IATO_MCP_Server::close_buffers()` closes whatever a tool call left open, on the tool and REST rollback paths, so nothing comes out ahead of the JSON response.

**Meta keys.** `IATO_MCP_Meta_Policy::ELEMENTOR_WRITABLE` (`_elementor_page_settings`, `_elementor_edit_mode`, `_elementor_template_type`) are the only `_elementor_` keys `update_post_meta` and `inherit_keys` may write; every other key under that prefix (element tree, element cache, CSS, SVG, caches, conditions, anything an addon adds) is refused with `elementor_content_key`, which names the Elementor tool to use. `set_page_settings` is unaffected. Rollback restores receipts verbatim (the before value is read from the receipts table, never from the request), so old `post_meta` receipts for now-refused keys still roll back. `decode_data()` accepts a tree stored as an array (pre-1.13.0 `update_post_meta` writes).

Tests: `tests/ElementorSanitizerTest.php`, `tests/ElementorWritePipelineTest.php`, `tests/MetaContentKeysTest.php` (stubs in `tests/stubs-meta.php`); live: `tests/wp-env/elementor-sanitize-live.sh` → `.py` with the test-only mu-plugin `tests/wp-env/mu-force-elementor-save-fail.php` (forces `Document::save()` to throw; lets the unfiltered filter return true) and the fixture seeder `tests/wp-env/create-sanitize-fixture.php`.

## Pages with Elementor turned off (1.16.0)

"Back to WordPress Editor" clears `_elementor_edit_mode` and keeps `_elementor_data`, so visitors see `post_content`, which Elementor's `Document::save()` replaces (`save_plain_text()`, `document.php:1401`). `IATO_MCP_Elementor_Adapter::builder_state()`: `active` (the flag is truthy, Elementor's own rule, or the post type is `elementor_library`, `e-floating-buttons` or `revision`, which never show classic content), `no_tree` (flag off, no data or a stored `[]`), `inactive_tree` (flag off with elements, or data that cannot be read).

| State | `update_elementor_data` | Other Elementor write tools | Receipt before value |
|---|---|---|---|
| `active` | writes as before | write as before | the stored tree; envelope when no elements are stored or the data cannot be read, because visitors see `post_content` then too |
| `no_tree` | sets the flag; sending `[]` is `elementor_empty_tree` | `not_elementor` with no data, `elementor_not_active` with a stored `[]` | envelope |
| `inactive_tree` | `elementor_not_active` unless `activate_builder: true` | `elementor_not_active` | envelope |

- **Gates, dry runs included:** `do_update_widget()`, `update_elementor_patch`, `update_elementor_data`, `IATO_MCP_Elementor_Atomic_Writer::apply()` and `rollback()`; `write_pipeline()` refuses as a backstop unless `$opts['set_builder_mode']`. `update_post_meta` refuses a truthy `_elementor_edit_mode` on these pages. Reads keep working.
- **The flag** is set in `write_pipeline()` after the tree is stored, so a refused save never switches visitors to the old tree. Results: `builder_mode_set`, `replaced_content_chars`; dry runs `would_set_builder_mode`, `would_replace_content_chars`.
- **The refusal** carries `content_chars` and `content_is_elementor_text` (`content_is_elementor_text()`, comparing visible text with `plain_text_of()`), for pages left by the bug before 1.16.0, when `update_elementor_data` did not set the flag. That only changes the wording; such a page is refused too and never activated automatically.
- **Rollback.** `IATO_MCP_Rollback::tree_receipt()` (`update_elementor_data`, `update_elementor_patch`) picks the before value: whenever the write turns the flag on or no elements are stored, it is `no_elementor_envelope( $content, $edit_mode, $tree )`, a JSON object, under the field `ACTIVATE_FIELD` (`elementor:document:activate`). `rollback_elementor()` restores all three. `envelope_with_content_after()` adds `content_after_sha256`, and `IATO_MCP_Rollback_Conflict` reports a conflict when the content differs from it and is not Elementor's own text of the current tree, so a classic edit made after activation is not silently overwritten. Reports: `restored` / `would_restore` `content_and_elementor_off`, or `content` when the flag was on.
- **Which envelopes count.** A before value is text from the post's data or an envelope, and both are JSON, so `ACTIVATE_FIELD`, a column no request can set, is what says the plugin wrote it. Under any other field (a receipt from before 1.16.0, or a stored value shaped like an envelope) the `elementor_data` key is ignored and the content goes through `clean_markup()` unless `IATO_MCP_Auth::holds_unfiltered_html()`.
- **Turning it back on.** Rolling back a `post_meta` receipt that turned `_elementor_edit_mode` off is a conflict if the post was modified since (`elementor_back_on()`).
- **Post content after a rollback.** A tree put back directly leaves `post_content` holding the text of the tree it replaced. `refresh_post_content()` brings it in line, except when Elementor is off or the page holds elements Elementor cannot load: `content_refreshed`, dry run `would_refresh_content`, on failure `content_note`, never a failed rollback. `plain_text_of()` uses `get_plain_text()` rather than `save_plain_text()`, which hides errors and can leave an output buffer open on a throw, corrupting the JSON response.
- **`get_page_builder`** adds `elementor_tree_present: true` to non-Elementor results. Server instructions tell clients to ask the user before activating.
- Known limits: content overwritten before 1.16.0 cannot be restored by the plugin, though WordPress revisions may hold it. Checked on Elementor Pro 4.3.3 with both an unbound key and an administrator's Application Password: a Theme Builder template with the flag off still accepts writes (it is `elementor_library`, which the state treats as `active`), and a page in that state on the same site is refused.
- Tests: `tests/ElementorWritePipelineTest.php`, `tests/RollbackActorConflictTest.php`, `tests/MetaContentKeysTest.php`; live: `tests/wp-env/rollback-actor-live.py` (the sections after "Elementor turned off").

## Undo records and table health (1.16.0)

A receipt is an undo promise, so `record()` checks its insert and never returns an ID that was not stored. Before 1.16.0 a meta key over 100 characters (`field` was `VARCHAR(100)`), a value the table's character set cannot hold, or a missing column lost the row silently, while the tool returned a `change_id` that rollback could not find. Invalid UTF-8 was suspected and is not a trigger: the database replaces the bytes when they are first stored.

- **`record()`.** On a failed insert it asks the table (`IATO_MCP_Schema::missing_columns()`, which works in any database language) and retries without the actor columns only if one is really missing, so a one-off failure such as a deadlock does not drop the actor. That receipt carries `warning` (`WARNING_NO_ACTOR`) and counts as a pre-1.13.0 receipt for the same-user rule; object capabilities still apply and clients cannot force this path. If nothing is saved: `change_id: null`, `stored: false`, `warning` (`WARNING_NOT_STORED`). The write is not reverted. Failures go in option `iato_mcp_receipt_failures`.
- **`slim()`** is the Elementor tools' receipt and keeps `stored` and `warning`. The bulk tool keeps a classic row's receipt when it has a warning.
- **`mark_rolled_back()`** retries with `rolled_back_at` alone when a `rolled_back_by_*` column is missing, because the mark is what stops a second rollback. If it still fails, `execute()` adds `warning`.
- **The call log** retries without its credential columns. The media phase log is unchanged.
- **`IATO_MCP_Schema::repair()`** (step 7, never throws) runs every table's `dbDelta`, which reports nothing, then `table_problems()`: expected columns come from each table's own `schema_sql()` through `column_definitions()`, compared in lower case, plus `REQUIRED_TYPES` (`field` must be `varchar(255)`). What is wrong is retried directly in `fix_directly()`, which also yields the database's own message, because `wpdb` clears `last_error` on every query. A problem is kept in option `iato_mcp_schema_health`, autoloaded and present only while there is one, so healthy sites do no work. It must not throw: a site that cannot be repaired still has to receive later steps, security steps included.
- **`maybe_repair()`** runs after `run()` on every request: at most hourly, at once when the plugin version changed, and on activation.
- **Diagnostics** shows both, with a button that repairs and clears the count (`admin_post_iato_mcp_diag_repair_tables`). `table_health_notice()` appears on the plugin's own pages only.
- Tests of the write-reach rules above and elsewhere in this file: `tests/MetaContentKeysTest.php`, `tests/ElementorWritePipelineTest.php`, `tests/McpServerCatchTest.php`, `tests/SeoCleanTextTest.php`; live: `tests/wp-env/write-safety-live.sh` → `.py` (installs Yoast SEO for its run when absent, and falls back to an older Yoast on an older WordPress).
- Tests: `tests/ReceiptStorageTest.php`, `tests/SchemaRepairTest.php`; live: `tests/wp-env/receipt-storage-live.sh` → `.py`, `tests/wp-env/schema-migration-live.sh` sections H and I (test-only mu-plugin `tests/wp-env/mu-schema-refuse-alter.php`). That suite rebuilds the tables before dropping columns: MariaDB's instant `DROP COLUMN` keeps counting a dropped column towards the row size limit, so repeated runs otherwise end in error 1118.

## `dry_run` (1.16.0)

`create_post`, `update_post`, `update_seo_data`, `assign_term`, `create_term`, `update_term` and `delete_term` ignored `dry_run` and really wrote until 1.16.0. They now run the same validation and capability checks and return `{dry_run: true, action, not_checked, ...}` with no write and no receipt. `action`: `would_create`, `would_update`, `would_assign`, `would_delete`, `no_change`. Updates carry `would_change` (`{field: {before, after}}`). ## Elementor's element cache (1.15.1)

`includes/class-element-cache-guard.php` (`IATO_MCP_Element_Cache_Guard`). Elementor keeps rendered pages in the `_elementor_element_cache` post meta, with dynamic widgets written as its `[elementor-element]` shortcode and a site-wide key (option `_elementor_element_cache_unique_id`). Neither is for clients.

- **Reads.** `_elementor_element_cache` is in `IATO_MCP_Meta_Policy::DENY_PATTERNS`. `scrub()` also replaces the key in every tool result (`handle_tools_call()`, which wraps `run_tool()`) and in the REST rollback route's responses.
- **Writes.** `run_tool()` refuses a call whose arguments hold the shortcode (`holds_shortcode()`: the raw string, without tags, URL and entity decoded, inside JSON strings) with `reserved_shortcode`, before the handler runs, unless `unfiltered_html_allowed()`. Tools named as reads are exempt (`is_read_tool()`: `get_`, `list_`, `find_`, `search_`, `resolve_`): they store nothing, and searching is how a site finds a shortcode stored earlier. It refuses rather than edits: removing text from sanitised markup can join what is left into a live attribute.
- **Render.** `write_pipeline()` step 5 removes Elementor's `elementor/element/should_render_shortcode` filter in a `finally`: Elementor removes it only when the render succeeds.
- **Upgrade.** Schema step 6 calls `refresh()`: a new key with `update_option` when one exists (Elementor creates a missing one without a lock), and the cached meta deleted. WP-Cron event `iato_mcp_element_cache_sweep`, 15 minutes later, deletes the meta again and purges page caches, because a render in progress can store the old key, which prints nothing. Cleared on deactivation and in `uninstall.php`. A replay (the schema option deleted by hand) makes one more key and one more rebuild, with the same end state.
- Tests: `tests/ElementCacheGuardTest.php`; live: `tests/wp-env/permissions-live.py`, `tests/wp-env/schema-migration-live.sh` sections F and G.

## Page caches and the `cache` object (1.15.0)

`includes/class-cache.php` (`IATO_MCP_Cache`). Spec: docs/mcp-api-spec-v2.md, "Reports on every write".

- **A write is what records a receipt.** `IATO_MCP_Change_Receipt::record()` calls `note_write()`; `IATO_MCP_Rollback::execute()` calls `note_rollback()` before the restore (a post it deletes can still be looked at, and a failed restore may have written). Response shapes cannot tell a write from a no-op. A value that did not change is skipped. Known limit: a Throwable after a write but before its `record()` leaves nothing pending, except that the pipeline's `clear_post_css()` also queues the post.
- **One point per tool call.** `IATO_MCP_Server::handle_tools_call()` calls `begin()` before the handler, then `finish()` (or `flush()` on the WP_Error and catch paths). `IATO_MCP_Rollback::handle()` does the same for the REST route. `finish()` splices `"cache":{…}` into the JSON text without decoding it, because a decode and re-encode turns `{}` into `[]`. Error results get the purge and no field. With nothing pending, a tool in `WRITE_TOOLS` without `dry_run` gets `purged: null, scope: null`; anything else comes back identical.
- **Scope.** `add_target()`: `menu_item`, `menu`, `menu_location`, `elementor_template`, `taxonomy`, `redirect`, `site_setting`, a missing post id, a `post` / `slug`, a `post` / `status` away from publish, rollback of `post` / `create` → `all`. `image` / `attachment` → `post_parent`, or the attachment. A post type in `SITE_WIDE_POST_TYPES` or with no public page (`is_post_type_viewable()`: an addon's hooks and snippets show up inside other pages) → `all`, with Elementor's global clear for `elementor_library` (the kit, Theme Builder, global widgets, saved templates), `e-floating-buttons` and anything built with Elementor. The rest → `post`. `route_alt()` calls `note_post()` for the page that asked.
- **Elementor CSS.** No write calls `files_manager->clear_cache()` any more except `finish()` for the site-wide post types and the fallback. `IATO_MCP_Elementor_Adapter::clear_post_css()` runs `clear_post_caches()` after every pipeline write and at the four meta sites (`update_post_meta`, `set_page_settings`, inherit, rollback), then queues the post. Reliable = the `Post` class exists, the delete did not throw, `_elementor_css` is gone; otherwise global clear + `all` + note. `finish()` rebuilds each queued post once with `Post::create($id)->update()`, only for `_elementor_edit_mode: builder`; a failed rebuild is a note, because Elementor rebuilds on the next view. Not rebuilt: when Elementor did not store the page, on the atomic path, and for a page holding elements Elementor cannot load right now (`unregistered_element_types()`): the file would miss their styles and Elementor would keep it after they come back. A write that said not to rebuild wins over a later one in the same call. Elementor CSS runs even with purging off: it is part of a correct write. Menus, terms, redirects and site settings leave it alone.
- **Order in `run_pending()`.** Elementor CSS first, then page caches, so nothing recaches a page linking to CSS about to go.
- **Integrations.** `integrations()` is data: slug → `present`, `post`, `all`, optional `home`. `purge( $scope, $post_id )` applies the `iato_mcp_cache_purge` filter, runs each plugin found, fires `iato_mcp_after_cache_purge` (also with no plugin, so a site can add its own). Return values are not read: `rocket_clean_post()` returns false after a valid purge, W3TC acts on shutdown, LiteSpeed through a response header. Differences from the obvious calls: `LITESPEED_PURGE_SILENT` is defined, or each write queues an admin notice; `did_action( 'litespeed_purged_all' )` skips a second full purge when Elementor's clear already caused one; `sg_cachepress_purge_everything()` for the full purge, since `sg_cachepress_purge_cache()` only targets the home URL path; WP Super Cache has no home step because `wp_cache_post_change()` does it and `wpsc_delete_url_cache()` refuses the home URL.
- **Caches it cannot purge.** `edge_notes()`: `CLOUDFLARE_PLUGIN_DIR`, `HOSTINGER_WORDPRESS_PLUGIN_VERSION`, `$_SERVER['H_PLATFORM']`, and a HEAD loopback to home (`cf-cache-status`, `cf-ray`, `x-hcdn-*`, `server: hcdn`, `x-litespeed-cache` when the plugin is absent). 2s timeout, transient `iato_mcp_cache_edge` for 12h, failures too, write path only; `get_site_info` reads the transient and never blocks. Hostinger Tools 3.0.79+ purges hCDN from `litespeed_purged_all`. On a live Hostinger site (LiteSpeed Cache 7.9.3, Hostinger Tools 3.0.80, 2026-11-04) post-scope writes cleared hCDN for the whole domain as well, within about 6 seconds, while LiteSpeed stayed `hit` on unrelated URLs. Nothing in Hostinger Tools explains that and the plugin does not control it, so the note stays.
- **Setting.** `iato_mcp_cache_purge_enabled`, `'1'` / `'0'`, default on, `IATO_MCP_Cache::is_enabled()`.
- Tests: `tests/CachePurgeTest.php`, `tests/CachePurgeAbsentTest.php` (a fresh process, so the real guards see nothing), `tests/CacheResponseTest.php` (stubs in `tests/stubs-cache.php`, fake Elementor `Post` in `tests/stubs-elementor.php`); live: `tests/wp-env/cache-purge-live.sh [dev|tests|legacy] [--plugins]` → `.py`, spy mu-plugin `tests/wp-env/mu-cache-spy.php`. `--plugins` installs LiteSpeed Cache, WP Super Cache, W3 Total Cache, WP Fastest Cache and SiteGround Optimizer one at a time. WP Rocket is a paid plugin: unit tests only. No local test runs a real LiteSpeed server: the suite checks the `X-LiteSpeed-Purge` header.

## Post dates and authors (1.19.0)

`includes/class-post-date.php` (`IATO_MCP_Post_Date`), `includes/tools/wp/tool-posts.php`. `from_args()` reads `date` and `date_gmt` into `{local, gmt}`, or null when neither was sent. Only `date_gmt` may carry `Z` or a zero offset, and the two must be the same moment (`date_mismatch`), so the second 01:30 of a clock change has to be named through `date_gmt` alone.

- **Status.** `resulting_status()` predicts `wp_insert_post()`, with the same one-minute margin: publish with a future date becomes `future`, `future` with a past date becomes `publish`. `update_post` compares that with the status asked for. A request for publish that would come out `future` is `future_date_on_published` unless `allow_future`, and this also covers publishing a draft that already has a future date. Anything that goes on or off the site because of a date needs the publish capability. `status_note` says so in the response.

## Chunked media uploads (1.19.0)

`includes/class-media-chunks.php` (`IATO_MCP_Media_Chunks`), `includes/class-media-uploader.php`, `includes/tools/wp/tool-media-upload.php`.

- **Checks in `ingest()`.** `sha256` is compared after decoding (`checksum_mismatch`). The declared `mime_type` must match the bytes, base64 and chunks only, because a caller naming a URL may not know what it serves. `structure_problem()` looks inside the file, because `getimagesize()` reads only the header and a transit-damaged file passes it: every required PNG chunk's CRC and the end marker, the JPEG end marker after walking past the metadata so a thumbnail's does not count, the GIF trailer by walking the blocks, the WebP length. It answers only when sure, since valid files carry trailing data, and it stops walking and passes the file after `MAX_WALK_STEPS` or `MAX_JPEG_MARKERS`, so a crafted one cannot take seconds. Optional PNG chunks are not checked, as browsers skip a bad one. AVIF is not checked. `wp_get_missing_image_subsizes()` decides the `warnings` and `missing_sizes`, because a small image legitimately has no sizes.
- **`ingest( $args, $user_id, $assembled )`.** A parameter rather than a source type, so no tool argument can name a path. It consumes the file, so `finish()` gives it a copy and keeps the chunks until an attachment exists.
- **Sessions.** `<id>.json`, written at start and when the first chunk sets the size, and `<id>.part`. The ID is 128 random bits and the client's filename is never in a path. `.htaccess` denies the folder on Apache and LiteSpeed; nginx ignores it, so the real protection there is unguessable names and extensions that do not run. Every chunk but the last must be the size of the first, so position and progress come from the file's size and nothing grows as an upload goes on. A chunk holds `flock` on the part file. `finish()` takes it without waiting and answers `upload_in_progress`.
- **A finish that stops.** Making image sizes can end the request, by time limit or memory. `ingest()` tells `finish()` the ID as soon as the attachment exists, through `$on_created`, and it goes in the session. A retry then calls `describe_attachment()` rather than making another: `recovered`, a warning, the receipt it never had, and whatever sizes are missing go to WP-Cron. If that attachment has been deleted since, it is made again.
- **Finish.** Size, then digest and image through `ingest()`. A refusal in `FINAL_CODES` removes the upload and says `upload_removed`. Anything else keeps it for a retry. On success the response is saved in the session and the part emptied, so a client that timed out gets the same result with `already_finished` and no second image. Both go an hour later.
- **Limits.** The lowest of 15 MB, `wp_max_upload_size()` and `iato_mcp_media_max_upload_size`, which is 10 MB by default. 4 KB decoded per chunk, five open uploads per user, 10,000 bytes each for `alt_text`, `title` and `caption`, because they sit in the session file. The rate limit is checked at start and counted at finish.
- **Cleanup.** Idle time, not age, because a large upload can take over an hour. Cron event `iato_mcp_media_chunks_cleanup`, hourly, and at each start, for sites with cron off. Cleared on deactivation. `uninstall.php` removes the folder.
- **Call log.** Successful chunk calls are not logged (`log_call()`): the log holds 200 rows. Failures are, without `data`.
- `IATO_MCP_Server::refusal()` is the shared JSON error. MCP clients see only the text, so a bare WP_Error's code and data never reach them.
- Tests: `tests/MediaIntegrityTest.php`, `tests/MediaChunksTest.php` (`tests/stubs-media-chunks.php`); live: `tests/wp-env/media-chunks-live.sh` → `.py`.

## `sanitized_report` and the inline markup opt-in (1.15.0)

**Report.** `includes/class-sanitize-report.php` (`IATO_MCP_Sanitize_Report`, pure PHP). `removed_text_remains()` keeps the "stay on the page as visible text" note to values where a removed style or script body really remains: an unclosed tag, Elementor's own kses pass, or WordPress below 6.5. Sanitising functions say nothing about what they removed, so input and output are each reduced to an inventory of tags and attributes (`inventory()`, lowercased, quotes respected, raw-text elements and comments skipped). `IATO_MCP_Elementor_Sanitizer` threads a report by reference next to `$changed`, never in static state, because `diff_tree` runs per bulk row and twice in dry runs; `diff_tree()` / `diff_settings()` return `report`. Surfaces: `write_pipeline()` → `pipeline_report()`, `sanitize_preview()`, atomic `build()` → `row_response()` (dedupes by path; `merge()` treats `…/title` and `…/title/value` as one value), `prepare_tree_write()` → `sanitized_report` in its return value, `add_to()` at the tool, the meta policy (`report` next to `changed`), `inherited_sanitized_report`. `create_post` / `update_post` (`iato_mcp_post_sanitize_report()`), the `create_media` description and plain text meta compare input with what was stored (`for_value()`, removals only: `&` to `&amp;` is not one). A kept-only entry comes without `sanitized`, so the report has its own gate wherever `sanitized` is copied.

**Whole elements (1.16.0).** `IATO_MCP_Elementor_Sanitizer::clean_markup()` is the markup rule for Elementor values, `create_post` / `update_post` content and the `create_media` description: `IATO_MCP_Inline_Markup::remove_style_and_script()` cuts STYLE and SCRIPT tokens with the scanner, then `wp_kses_post` runs, always last, because cutting text out of sanitised markup can join what is left into something live. Below WordPress 6.5 the tokenizer does not exist and the value goes to kses unchanged. `write_pipeline()` step 5 renders with no inline CSS. CSS already on pages as text is not cleaned up: a tool cannot tell it from real content.

**Opt-in.** `includes/class-inline-markup.php` (`IATO_MCP_Inline_Markup`), `includes/class-html-token-scanner.php` (loaded on demand: it extends `WP_HTML_Tag_Processor`). Setting `iato_mcp_inline_markup_enabled`, `'1'` / `'0'`, default off.

- **It does not grant `unfiltered_html`.** The kses lock stays on for the request. `policy()` reads the capability inside `write_unlocked()`, requiring `unfiltered_html` and `manage_options` (an Editor holds the first; the setting says administrators). User 0 holds neither. `unfiltered_html_allowed()` is unchanged. Works on OAuth, bound key and Application Password.
- **One value.** `IATO_MCP_Elementor_Sanitizer::walk()` knows the element and passes `$html_widget`; `diff_value()` applies `sanitize_html_setting()` only to exactly `<id>/settings/html` of `elType: widget`, `widgetType: html`. `sanitize_value()` cannot host this: it sees a sliced path, and `styles/html` looks the same. The meta policy calls `sanitize_value()` and is untouched.
- **Never a regex to find style blocks.** `<img alt="<style>" src=x onerror=alert(1) x="</style>">` survives regex extraction + kses + reinsertion. `filter()` finds real STYLE tokens with `next_token()` (SCRIPT tokens are dropped whole, since 1.16.0), puts `sanitize_css()`'s result behind `random_bytes` placeholders (exactly one occurrence required), runs `wp_kses` with `wp_kses_allowed_html( 'post' )` plus the SVG subset, rebuilds each opening tag (`media` only), and `passes_final_check()` walks the result: any tag or attribute outside the lists, or a paint `url()` that leaves the document, fails the value (`stripped_unsafe`), and the caller uses the plain rule. That walk is also what stops `<title><a href="</title><img onerror=…>">`: kses keeps attribute values, browsers read `<title>` as raw text. Needs WordPress 6.5 (`next_token()`); below that `stripped_wp_version`.
- **`sanitize_css()` is a tokenizer, not regexes.** Regexes were tried and an independent review bypassed them with real off-site requests in Chrome: `--x:"url(";background:url(https://evil/)` hides the second url(), deleting `@import x;` from `@im@import x;port "…"` assembles a new @import, nested parentheses and `var()` escape an `image-set()` pattern. `css_tokens()` follows CSS Syntax Level 3 for strings, url(), functions, at-keywords and escapes, and returns null for what a browser would repair but this will not guess at (an unterminated string, comment or url(), a bad url()). `rewrite_css()` removes `@import` to its `;`, off-site `url()` becomes `none`, an off-site string outside an attribute selector becomes `""`, and a function is replaced with `none` when anything inside leaves the site (`function_leaves_site()`: in a function that takes an image or URL every string counts as a URL, and any nested function but url(), gradients and colours counts as one, because var(), attr() and if() can hand it a value nothing here can see). `url_stays_on_site()`: a fragment, relative, this host or `data:image/`; whitespace is stripped and a backslash refuses it, because URL parsers read `/\evil.example` as `//evil.example`. `css_final_check()` reads the result again: the tokens and a plain search of the decoded text must agree (`url(` counts match, no `@import`), so a block fooling the tokenizer has to fool the search too. `text_leaves_site()` (1.16.0) is the rule that knows nothing of CSS: with whitespace removed and escapes decoded, wherever a URL can begin, the text up to the first `/ ? #` or backslash must be this site's host exactly, with no URL parsing, because `parse_url()` on a loosely cut string read `//evil.example);--a:@localhost/` as a host of localhost. Base64 images, `a[href^="https://"]` and SVG's three namespace URLs pass. `style_attribute_leaves_site()` applies the tokenizer and then this to style attributes in `passes_final_check()`. It is strict on purpose: a block with a URL in an attribute selector or text that names another site is dropped whole, as is a `url(https://this.site)` with no path, or an SVG data URL using another namespace written in plain text. It exists because a third review (with Chrome) again made the tokenizer and the browser disagree: a dimension (`1url(`) or hash (`#url(`) read as url(), and an escape before a multibyte character cut in half. Off-site `<img>`, `<video>` and `<audio>` are outside this: `wp_kses_post` keeps them everywhere, so the opt-in adds no reach there, and what matters is a request conditional on page content through a selector. Known limit: `background:var(--x)` in a block can take a value from a `style` attribute in another widget, which core's filter allows. Whole block dropped: invalid UTF-8 or control characters, `<`, a character reference (`&#` or `&name`: a browser decodes them in a style element inside `<svg>`, so `@&#105;mport` is @import there), `expression(`, `behavior:`, `-moz-binding`, `javascript:`, `vbscript:`, or `@import` / `url(` / `image-set(` visible only after decoding. `passes_final_check()` also decodes CSS escapes on SVG attributes (`fill="u\72l(…)"`).
- **Keys are lowercase.** `wp_kses` compares lowercased names, so a `viewBox` key strips the attribute; `viewbox` is what it stores and browsers restore it (checked in Chrome).
- **`post_content`.** Elementor's plain-text render keeps `<style>`, and core's content kses then leaves the CSS as text. `write_without_style_in_content()` adds a priority-9 `content_save_pre` filter around `Document::save()` and the step-5 render whenever the tree holds a style block: one stored earlier stays in the tree after the setting is turned off or another user edits the page.

**What a URL is.** `with_url_kind()` asks WordPress, because path guessing was wrong on common URLs: `query_vars_of()` walks `$wp_rewrite->wp_rewrite_rules()` as `url_to_postid()` does, then lets the query string win, and `WP_Query::parse_query()` (flags only, no posts) decides. A term or author that does not exist is `404` (`get_queried_object()`), and so is a date or a later page with no posts (`has_posts()`, `WP::handle_404()`'s rule). The kinds: `singular`, `blog`, `archive`, `date`, `search`, `404`, `other_host`, `unknown`. `unknown` never gets a confident answer: a feed, a URL with two archive kinds at once, a post named in the query string with no rewrite, a path under plain permalinks, WooCommerce's shop page and product archives, whose conditions are WooCommerce's. On `unknown` only Entire Site applies and every other condition goes under `not_evaluated`. `url_to_postid()` answers with the static front page for a home URL with a query, so on `archive`, `date`, `search` and `404` the post ID is dropped (`rendering_post_id` null). `detect_archive_info()`'s guess stays for one case: WordPress says not found, and a plugin's term or author link really produces the URL (it found the object). `route_type` gained `taxonomy_archive`, `date_archive`, `search_results` and `blog_home`.

**Which conditions shadow a URL.** `condition_matches_context()` takes the URL's kind, following Pro's rules: `include/singular` matches singular and not-found pages only, so not the posts page or a search, however much a post ID is known; `include/singular/not_found404` matches a not-found page; `include/archive/post_archive` matches the blog home alone (before 1.17.0 it matched any URL that was not a recognised archive, so a blog-archive template took the blame for ordinary pages); `include/archive` also matches the blog home, searches and date archives; and `date`, `search`, `author` and `include/singular/front_page` are understood. A posts-listing home page is not singular, so `front_page` does not match it, as in Pro.

**`theme_locations`.** `IATO_MCP_Elementor_Router::theme_locations()`: `{header, footer}`, each `{template_id, condition_matched}` or null; null as a whole when Pro's Theme Builder is not loaded or reading it fails. `get_documents_for_location()` cannot answer this: it is bound to the current request, here the REST call, not the URL asked about. So `location_template()` applies the rule of Pro's `Conditions_Manager::get_location_templates()` (checked against Pro 4.3.3's source) to the URL: Pro's conditions cache (`get_cache()->get_by_location()`, which decides what renders, so a template whose conditions did not reach it is rightly absent), published only (the cache holds drafts too), any matching exclude removes the template, the last matching include sets its priority, the lowest priority wins, a tie goes to the first in the cache. `location_condition()` returns a priority, false, or null when it depends on something this code does not look at: child-of, by-author and in-term conditions, and anything on an `unknown` URL, which go under `not_evaluated`, with `template_id` and `condition` for administrators and `location` alone for others. A page on Elementor Canvas, its own or the kit's default for a page built with Elementor that named neither Elementor's template nor the theme's (`page_template_hiding_locations()`, as Elementor's PageTemplates module chooses), gets null for both with `hidden_by_page_template`: Pro drops its header and footer there (`filter_page_template_locations()`) and `canvas.php` prints the theme's neither. Another host gives `theme_locations: null` and no shadowing. Tests: `tests/ElementorRouterTest.php` (a fake Pro in `tests/stubs-pro.php`).

Known limits: `find_via_theme_builder_module()` is still bound to the REST request. `theme_locations` names the template the conditions point at: the `elementor/theme/get_location_templates/template_id` and `condition_sub_id` filters, which multilingual plugins use to swap in a translation, are not applied. WooCommerce's shop page and product archives stay `unknown`. `?page=99` past a post's own pages is not noticed.

A failure or a throw, including another plugin's `save_post` hook during the publish, reaches `iato_mcp_template_take_down()`: it trashes the template and rebuilds Pro's cache, each guarded because the same hooks run again, purges page caches if it had gone live, and says what is left: `trashed_template_id`, or `template_id` with `still_live: true`. `create_document()` trashes a post Elementor left without a version, and one left behind by a throw, which it finds by watching `wp_insert_post`.

Conditions go through Pro's `save_conditions()`, never the meta alone: Pro's cache decides what renders. ## Elementor Atomic (Editor V4) Reader

`includes/class-elementor-atomic.php` — `IATO_MCP_Elementor_Atomic`. Pure-PHP normalisation layer for Elementor 4.x atomic elements stored in `_elementor_data` (`e-heading`, `e-paragraph`, `e-image`, `e-button`, `e-flexbox`, `e-div-block`, …). It reads stored data only; its one Elementor call (since 1.13.1) is a guarded, cached lookup of an element type's registered props schema (`schema_props()`, through the resolver seam), so reads work on Elementor 3.x, 4.0–4.2, with the Elementor MCP module off, and with Elementor deactivated.

- **Detection**: a node is atomic iff `elType` or `widgetType` starts with `e-`, or any top-level setting is a typed envelope. The stored `version` key is not a signal (Elementor writes `"0.0"`, never `4`).
- **Envelopes**: settings are `{"$$type": key, "value": payload, "disabled"?: true}`. `unwrap()` flattens them (text family `string|html|escaped-html|html-v2|html-v3` → string, `url` → string, `query` → `{post_id,label}`, `attributes` → map, `dynamic` → `{"$dynamic": …}`, unknown types recurse). `plain_settings()` also fills unsaved schema defaults from `includes/data/elementor-atomic-defaults.php` and reports them in `defaulted_keys`.
- **Normalised view** (`normalize()`): `schema: "atomic"`, rendered `tag`, and the same peek keys classic widgets emit (`title`, `header_size`, `editor`, `text`, `link`) plus `link_new_tab`, `link_post_id`, `image_url`, `image_id`, `image_alt`, `image_alt_source` (`attachment` for Media Library images, `element` for URL images).
- **Wiring**: `IATO_MCP_Elementor_Adapter::peek_fields()` delegates to it; every node from `flatten_widgets` / `summary` / `find_by_filter` carries `schema: classic|atomic`; `matches_filter()` evaluates atomic nodes against `match_settings()` (plain values + derived `header_size`, `editor`, `link_url`, `image_*`). `get_elementor_widget` adds `settings_plain`, `defaulted_keys`, `tag`, `peek` for atomic nodes while keeping `settings` raw. `get_page_builder` adds `elementor_schema: classic|atomic|mixed|empty`. `initialize` advertises `capabilities.elementor.atomic_read`.
- **WP calls** (attachment alt/URL, permalink) go through an injectable resolver (`set_resolver()`), which is how the unit tests run without WordPress.
- **Stored-value check (1.13.1).** `has_atomic_type()` is the detection used by writes and this check. When Elementor's registry knows the type, its class decides (atomic only with `get_props_schema()`: e-addons' classic `e-iframe` stays classic); when it cannot say (type unregistered, Elementor inactive), an element is atomic only with the `e-` prefix and an envelope-shaped setting. Only `e-` types and envelope-shaped elements reach the registry (`type_info` resolver op, cached), so classic pages never start Elementor's widget registry on reads. `invalid_keys()` lists settings stored without their envelope (what 1.12.x / 1.13.0 stored for plain values: Elementor then drops the link or image and refuses to save the page); with the registered schema only schema keys are checked, without it every top-level setting (Elementor 4.x stores every atomic setting as an envelope: each prop type's `validate()` requires one). `normalize()` adds `stored_value_invalid: true` + `invalid_keys` and derives no peek field from those keys; `plain_settings()` shows them as stored; `get_elementor_widget` carries the flags at the top level; `get_elementor_data` lists `invalid_elements` at the top level in every format (raw and compact data stay as stored). Valid pages carry no flag.
- **Writes to atomic elements (1.13.1 guard).** Since 1.14.0 the guard applies only where the atomic writer is unavailable (Elementor before 4.3.0, the Atomic Editor off, the element type not registered; `IATO_MCP_Elementor_Atomic_Writer::unavailable()`): `do_update_widget()` (so `update_elementor_widget`, `set_widget_setting`, `update_elementor_widgets_bulk`) refuses, dry runs included, any value that is not a `$$type` envelope (null too) and any key outside the registered schema (`IATO_MCP_Elementor_Adapter::atomic_value_refusal()`: element ids, plain/unknown keys, an example typed value from the stored `$$type` or the schema; `tool_error()` turns it into an isError result with JSON text). With plain values the code is `atomic_write_unavailable` and the message names what is missing; with unknown keys alone it stays `atomic_plain_value_unsupported`. `update_elementor_patch` / `update_elementor_data` refuse through `IATO_MCP_Elementor_Atomic::tree_changes()` (changed or new top-level settings that are not envelopes; paths inside `…/value` and removals pass; elements damaged earlier and left unchanged block nothing). Typed values go through as in 1.13.1. Everywhere else the writer below handles atomic targets.

## Elementor Atomic (Editor V4) writer (1.14.0)

`includes/class-elementor-atomic-writer.php` — `IATO_MCP_Elementor_Atomic_Writer`; Elementor's code behind `includes/class-elementor-atomic-engine.php` — `IATO_MCP_Elementor_Atomic_Engine` (every call guarded; replaced by a fake in tests with `set_engine()`). ## SEO Plugin Adapter

`class-seo-adapter.php` detects which SEO plugin is active and reads/writes accordingly.

Priority order:
1. Yoast SEO (`wordpress-seo/wp-seo.php`) — meta keys: `_yoast_wpseo_title`, `_yoast_wpseo_metadesc`
2. RankMath (`seo-by-rank-math/rank-math.php`) — meta keys: `rank_math_title`, `rank_math_description`
3. SEOPress (`seopress/seopress.php`) — meta keys: `_seopress_titles_title`, `_seopress_titles_desc`
4. Fallback — native WP title, empty description

Detection via `is_plugin_active()`. Cache result in a static property for the request lifetime.

Text goes through `IATO_MCP_SEO_Adapter::clean_text()`, on reads too, rather than `sanitize_text_field()`, which removes anything shaped like `%xx`: `%%category%%` became `%tegory%%` and `%%date%%` became `%te%%` (1.16.0).

## `get_iato_seo_fixes` — issue types

The bridge tool handles five fixable issue types from IATO's SEO issues endpoint:

| Issue type | Can auto-fix | Fix method |
|---|---|---|
| `title` | Yes | SEO adapter `update_title()` |
| `meta_description` | Yes | SEO adapter `update_description()` |
| `alt_text` | Yes | `update_alt_text` WP tool |
| `h1_missing` | No | Return as `fix_type: manual` with instructions |
| `h1_duplicate` | No | Return as `fix_type: manual` with instructions |
| `canonical` | No | Return as `fix_type: manual` with instructions |

Manual fix items include `manual_instructions` in the response so Claude can surface them to the user.

Since 1.14.0 issues the WordPress tools cannot act on are left out of `issues` and listed under `skipped` (`{issue_type, url, title, reason}`): `other_domain` for a URL whose host is not the site's (compared without case and a leading `www.`; `iato_mcp_url_on_this_site()`), `not_a_wordpress_post` for a URL on the site that `url_to_postid()` does not resolve (archives, files, no URL, `mailto:`). `total`, `auto_fixable` and `manual` count the fix list only.

## Post Meta Policy

`includes/class-meta-policy.php` — shared by `get_post_meta`, `update_post_meta`, `set_page_settings`, `set_featured_image`, and `update_elementor_data` (when `inherit_settings_from` is used).

Two layers:
1. **Denylist** (hard-reject even with `force=true`): keys matching credential / auth / capability patterns — `*_token*`, `*_secret*`, `*_api_key*`, `*_password*`, `*_credential*`, `_oauth_*`, `_jwt_*`, `_refresh_token_*`, `_elementor_element_cache*`, `wp_capabilities`, `wp_user_level`, `wp_user_roles`, `session_tokens`, `wp_2fa_*`. Case-insensitive substring match.
2. **Allowlist** (writable without `force=true`): public custom meta (any key not starting with `_`) plus known-safe prefixes — `site-`, `ast-`, `footer-sml-`, `_elementor_`, `_wp_page_template`, `_thumbnail_id`, `_yoast_`, `_genesis_`, `_kadence_`, `_generate_`, `rank_math_`, `_seopress_`.

Anything not in the denylist and not in the allowlist requires `force=true` on writes and returns `meta_requires_force`. Since 1.16.0 so does a key with spaces or characters outside ASCII (`check_write()`), and `check_stored_key()` applies to `update_post_meta`, `inherit_keys` and rollback's preflight: see "Coding Rules".

Since 1.13.0: `IATO_MCP_Meta_Policy::capability_for_key()` names keys that need an administrator beyond `edit_post` (`ADMIN_ONLY_KEYS`: `_elementor_template_type`); `update_post_meta` refuses them, and `update_elementor_data`'s inherit step skips them for other users (`inherited_skipped` reason `requires_manage_options`). Array values under non-Elementor keys go through `sanitize_array_value()` in `update_post_meta`, `set_page_settings` and inherit: strings containing `<` that the write changes are filtered with `wp_kses_post` (the sanitizer's markup rule), values equal to the stored ones are kept verbatim, paths reported in `sanitized_paths`; skipped when unfiltered HTML is allowed. `get_post_meta` redacts denylist hits unconditionally and filters out underscore-prefixed keys outside the allowlist unless `include_protected=true`.

## Media Uploader

`includes/class-media-uploader.php` — implements `create_media`. Sources:
- `base64` (default, recommended): bytes decoded in-process; no outbound HTTP.
- `url` (opt-in via setting + host allowlist): SSRF guards resolve the host, reject private/loopback/link-local/cloud-metadata IPs, use `wp_safe_remote_get` with hard timeout + redirect cap, re-validate every redirect destination IP.

Always: MIME verified via `wp_check_filetype_and_ext()` against actual bytes (not the claimed `mime_type`); image-only allowlist (`jpeg`, `png`, `gif`, `webp`, `avif`); SVG hard-rejected this release; size + dimension caps; per-user rate limit transient. Uses `wp_handle_sideload()` + `wp_generate_attachment_metadata()` for the actual filesystem write and intermediate-size generation.
